% Proposed Framework: AnimatorSBT

We propose \textbf{AnimatorSBT}, a framework designed to integrate Soulbound Token issuance
into the anime production workflow through an existing production management tool.
This section describes the system architecture (\cref{subsec:architecture}),
the SBT metadata schema (\cref{subsec:metadata}),
the issuance flow (\cref{subsec:flow}),
the verification mechanism (\cref{subsec:verification}),
and privacy considerations (\cref{subsec:privacy}).

% ----- 4.1 System Architecture -----
\subsection{System Architecture}
\label{subsec:architecture}

AnimatorSBT consists of four components:

\begin{enumerate}
  \item \textbf{Production Management Client (PMC):}
    A Progressive Web Application (PWA) used by freelance animators to track
    their daily work---cut assignments, task status, deadlines, and deliverables.
    This is the primary data source for contribution records.
  \item \textbf{AnimatorSBT Smart Contract:}
    An ERC-721--based~\cite{entriken2018erc721} non-transferable token contract deployed on a Layer~2 blockchain
    (Polygon Proof of Stake (PoS)). The contract enforces soulbinding by overriding transfer functions
    and provides minting, revocation, and metadata retrieval interfaces.
  \item \textbf{Issuance Service:}
    A lightweight backend that bridges the PMC and the smart contract.
    Upon project completion (or at a user-defined milestone),
    the service constructs SBT metadata from the PMC's work logs,
    uploads it to the InterPlanetary File System (IPFS)~\cite{benet2014ipfs},
    and triggers the minting transaction.
  \item \textbf{Verification Portal:}
    A public web interface where third parties (studios, clients, recruiters)
    can verify an animator's contribution history by querying the blockchain
    and rendering the associated metadata.
\end{enumerate}

\textbf{Why blockchain rather than a centralized database?}
A conventional approach would store contribution records in
a centralized database operated by a single entity (e.g., TOONIQ or a studio).
However, this fails to satisfy the requirements defined in \cref{subsec:formalization}
for three reasons:
\begin{enumerate}
  \item \textbf{Persistence beyond any single organization:}
    Anime studios frequently close or restructure.
    A centralized database disappears with its operator.
    On-chain records persist independently of any company's survival---
    even if TOONIQ ceases operations, every SBT remains verifiable on the public blockchain.
  \item \textbf{Cross-organizational portability:}
    Freelance animators work across dozens of studios over their careers.
    In a centralized model, each studio holds a fragment of an animator's history
    in its own siloed system, with no standard way to aggregate them.
    With SBTs, all credentials accumulate in a single wallet address.
    An animator can present one link to a verifier
    and prove their entire cross-studio career history.
  \item \textbf{Tamper resistance without trust:}
    A centralized database administrator can modify or delete records.
    Blockchain records are append-only and cryptographically linked;
    once an SBT is minted, neither the issuer nor any third party
    can alter the fact that it was issued, when, and to whom.
    This provides animators with an independent guarantee
    that their credentials cannot be retroactively revoked or falsified
    without an auditable on-chain trace.
\end{enumerate}

\textbf{Why SBTs rather than Verifiable Credentials?}
An alternative design would use W3C Verifiable Credentials (VCs)~\cite{sporny2022vc}
instead of on-chain SBTs.
VCs offer mature standards, selective disclosure, and off-chain storage,
making them well suited for scenarios where a trusted issuer exists
and credentials are presented bilaterally (e.g., university diplomas).
However, VCs have a critical limitation in the anime production context~\cite{kakebayashi2023sbt}:
\textit{verification depends on the issuer remaining operational.}
If the issuing studio closes---a common event in the anime industry---VC
verification fails unless a third party maintains the issuer's key material.
SBTs avoid this dependency: the on-chain record persists regardless of
the issuer's survival, and any party can verify ownership
by querying the public blockchain.
Additionally, SBTs provide a naturally aggregatable portfolio---all
credentials accumulate at a single wallet address, queryable in one call---whereas
VCs require the holder to manage and selectively present individual credentials
from a local wallet, adding friction that conflicts with requirement R5 (minimal friction).
We note that SBTs and VCs are not mutually exclusive:
future work (\cref{sec:conclusion}) explores VC-compliant wrappers
for AnimatorSBT metadata.

A key design principle is \textbf{transparency to the end user}:
the animator does not need to understand blockchain technology,
manage a wallet manually, or pay gas fees.
The PMC handles wallet creation (embedded wallet via account abstraction~\cite{buterin2021erc4337})
and the Issuance Service sponsors gas fees through a relayer.
From the animator's perspective, the experience is:
``I finished my cuts $\rightarrow$ I got a certificate in my profile.''

% ----- 4.2 SBT Metadata Schema -----
\subsection{SBT Metadata Schema}
\label{subsec:metadata}

Each AnimatorSBT encodes a structured record of a single project contribution.
The metadata follows a JSON schema stored on IPFS, with the content hash
referenced by the on-chain token URI. \Cref{tab:metadata} defines the schema.

\begin{table}[ht]
\centering
\caption{AnimatorSBT metadata schema.}
\label{tab:metadata}
\footnotesize
\begin{tabular}{@{}llp{3.2cm}@{}}
\toprule
\textbf{Field} & \textbf{Type} & \textbf{Description} \\
\midrule
\texttt{project\_title}    & string   & Anime project title \\
\texttt{episode}           & string   & Episode or segment ID (nullable) \\
\texttt{role}              & enum     & e.g., \texttt{key\_anim}, \texttt{in\_between}, \texttt{coloring} \\
\texttt{task\_count}       & integer  & Tasks completed (cuts, frames) \\
\texttt{period\_start}     & date     & Contribution start date \\
\texttt{period\_end}       & date     & Contribution end date \\
\texttt{studio}            & string   & Contracting studio (nullable) \\
\texttt{issuer}            & address  & Issuing entity address \\
\texttt{issued\_at}        & datetime & ISO~8601 issuance timestamp \\
\texttt{evidence\_hash}    & bytes32  & Keccak-256 of work log data \\
\texttt{schema\_version}   & string   & Schema version (e.g., ``1.0.0'') \\
\bottomrule
\end{tabular}
\end{table}

The \texttt{evidence\_hash} field provides a cryptographic link between the on-chain certificate
and the off-chain work log stored in the PMC.
This allows verifiers to confirm that the SBT corresponds to actual recorded work
without exposing the raw work log data.

The \texttt{studio} field is intentionally nullable to accommodate cases where
non-disclosure agreements prevent public attribution to a specific project or studio.
Even without a studio name, the SBT still certifies the animator's role, task volume,
and time period, providing more information than the current system of no record at all.

% ----- 4.3 Issuance Flow -----
\subsection{Issuance Flow}
\label{subsec:flow}

The SBT issuance process follows five steps,
illustrated in \Cref{fig:issuance_flow}:

\begin{figure}[t]
  \centering
  \includegraphics[width=0.85\columnwidth]{figures/issuance_flow}
  \caption{Five-step SBT issuance flow. The animator's only interaction
  is with the PMC (Step~1); all subsequent steps are automated.}
  \label{fig:issuance_flow}
\end{figure}

\begin{enumerate}
  \item \textbf{Work Recording:}
    The animator logs their daily work in the PMC as part of their normal workflow
    (cut assignments, status updates, completion timestamps).
    No additional effort is required for SBT issuance.
  \item \textbf{Milestone Trigger:}
    When a predefined milestone is reached (e.g., project completion, episode delivery,
    or manual request by the animator), the PMC sends a certification request
    to the Issuance Service.
  \item \textbf{Metadata Construction:}
    The Issuance Service aggregates the work log entries for the specified period,
    computes the \texttt{evidence\_hash}, constructs the JSON metadata, and uploads
    it to IPFS via a pinning service (e.g., Pinata).
  \item \textbf{Minting:}
    The Issuance Service calls the \texttt{mint()} function on the AnimatorSBT
    smart contract, passing the animator's wallet address and the IPFS content URI.
    Gas fees are covered by the Issuance Service through a meta-transaction relayer
    (ERC-2771).
  \item \textbf{Confirmation:}
    The PMC receives a transaction receipt and displays the newly issued SBT
    in the animator's profile, including a link to the Verification Portal.
\end{enumerate}

\textbf{Example scenario.}
Consider a freelance key animator, Tanaka, who is assigned 25 cuts
for Episode~7 of an anime series through a secondary subcontractor.
Over six weeks, Tanaka logs each cut assignment, status update,
and completion in the PMC as part of her normal workflow.
When Episode~7 wraps, the PMC triggers a certification request.
The Issuance Service aggregates Tanaka's work log
(role: \texttt{key\_anim}, task count: 25, period: 2025-04-01 to 2025-05-15),
computes the evidence hash, and mints an SBT to her embedded wallet.
Tanaka sees a new certificate in her PMC profile.
Three months later, when applying to a different studio,
she shares her wallet address.
The studio queries the blockchain, confirms she completed 25 key animation cuts
on a real production, and offers her a contract---even though
her name never appeared in the episode's broadcast credits.

% ----- 4.4 Verification Mechanism -----
\subsection{Verification Mechanism}
\label{subsec:verification}

Third parties can verify an animator's credentials through two methods:

\textbf{On-chain query:}
Given an animator's wallet address (or an Ethereum Name Service (ENS) name / human-readable identifier),
a verifier can query the AnimatorSBT contract's \texttt{balanceOf()} and
\texttt{tokenURI()} functions to retrieve all issued SBTs and their metadata.
Since the tokens are non-transferable, possession of an SBT at a given address
constitutes proof that the address holder earned the credential.

\textbf{Verification Portal:}
A web-based interface renders an animator's SBT portfolio in a human-readable format,
displaying project titles, roles, task counts, and time periods.
The portal also verifies the \texttt{evidence\_hash} against the PMC's stored work logs
(with the animator's consent) to provide an additional layer of authenticity.

% ----- 4.5 Privacy Considerations -----
\subsection{Privacy Considerations}
\label{subsec:privacy}

AnimatorSBT addresses privacy through several mechanisms:

\begin{itemize}
  \item \textbf{Minimal on-chain data:}
    Only the token ID, owner address, and IPFS URI are stored on-chain.
    All detailed metadata resides on IPFS and can be encrypted if needed.
  \item \textbf{Nullable fields:}
    Sensitive information (studio name, project title) can be omitted
    when non-disclosure agreements (NDAs) apply, while still certifying role and task volume.
  \item \textbf{Selective disclosure:}
    The animator controls which SBTs are visible on the Verification Portal.
    Non-public SBTs can be shared via direct links with access control.
  \item \textbf{Embedded wallets:}
    By using account abstraction (ERC-4337), animators do not need to manage
    private keys directly, reducing the risk of key loss or social engineering attacks.
  \item \textbf{Right to be forgotten:}
    While blockchain data is immutable, the smart contract includes a
    \texttt{revoke()} function that marks an SBT as invalidated.
    The IPFS metadata can also be unpinned, rendering it inaccessible
    through standard gateways (though the on-chain record of revocation persists).
\end{itemize}
