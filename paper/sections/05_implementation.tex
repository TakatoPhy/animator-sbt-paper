% System Design and Technical Specification

This section presents the technical specification of the AnimatorSBT framework,
including the technology stack (\cref{subsec:stack}),
the smart contract design (\cref{subsec:contract}),
the prototype implementation deployed on a public testnet (\cref{subsec:prototype}),
and the integration design with an existing production management client (\cref{subsec:integration}).

% ----- 5.1 Technology Stack -----
\subsection{Technology Stack}
\label{subsec:stack}

The proposed system uses the following components:

\begin{itemize}
  \item \textbf{Blockchain:} Polygon PoS~\cite{gangwal2023layer2} (targeted for production deployment). Polygon was selected for its low
    transaction costs (on the order of $10^{-3}$~USD per mint at typical gas prices;
    see \cref{tab:gas}), Ethereum Virtual Machine (EVM) compatibility, and established ecosystem.
  \item \textbf{Smart contract:} Solidity 0.8.20 with OpenZeppelin Contracts v4.x
    (ERC-721, AccessControl, Counters). We note that OpenZeppelin Contracts v5 has
    since superseded the \texttt{\_beforeTokenTransfer} hook used here with a unified
    \texttt{\_update} hook and removed the \texttt{Counters} utility; porting to v5
    (using \texttt{\_update} for soulbinding enforcement and a plain counter) is a
    straightforward, recommended step for a production deployment, which we note as
    future work.
  \item \textbf{Metadata storage:} IPFS via Pinata pinning service.
    Metadata JSON files are content-addressed and immutable once pinned.
  \item \textbf{Issuance service:} Node.js backend using ethers.js v6
    for blockchain interaction and Pinata SDK for IPFS uploads.
  \item \textbf{Production management client:} Progressive Web Application (PWA)
    built with a standard web framework, providing cut management,
    deadline tracking, and income calculation features for freelance animators.
  \item \textbf{Wallet management (production target):} Embedded wallets via account abstraction
    (ERC-4337), eliminating the need for animators to install
    wallet software or manage private keys.
    The current prototype uses standard externally owned accounts (EOAs);
    ERC-4337 integration is planned for the production deployment.
\end{itemize}

% ----- 5.2 Smart Contract -----
\subsection{Smart Contract Design}
\label{subsec:contract}

The \texttt{AnimatorSBT} contract is designed to extend OpenZeppelin's ERC-721 implementation
with two key modifications: \textbf{soulbinding} and \textbf{role-based access control}.

\subsubsection{Soulbinding Mechanism}

Transfer restriction is enforced by overriding the \texttt{\_beforeTokenTransfer}
hook, which is called on every token movement including minting, transferring, and burning:

\begin{lstlisting}[basicstyle=\footnotesize\ttfamily, frame=single,
  caption={Soulbinding enforcement via transfer hook.},
  label={lst:soulbind},
  morekeywords={function,address,uint256,internal,virtual,override,if,revert,super}]
function _beforeTokenTransfer(
  address from, address to,
  uint256 tokenId, uint256 batchSize
) internal virtual override {
  // Allow mint (from==0), block transfers
  if (from != address(0)
      && to != address(0)) {
    revert SoulboundTransferDisabled();
  }
  super._beforeTokenTransfer(
    from, to, tokenId, batchSize
  );
}
\end{lstlisting}

Additionally, the \texttt{approve()} and \texttt{setApprovalForAll()} functions
are overridden to revert unconditionally, preventing any approval-based transfer mechanisms.
This ensures that SBTs cannot be transferred through any ERC-721--compliant interface.

\subsubsection{Why Not ERC-5192?}

The ERC-5192 standard~\cite{daubenschuetz2022erc5192} defines a minimal interface
for soulbound NFTs via a \texttt{locked()} query function and a lock event.
ERC-5192 and our approach address complementary concerns rather than competing
ones: ERC-5192 is primarily a \emph{signaling/interoperability} standard (it lets
SBT-aware tooling discover that a token is non-transferable), whereas our contract
focuses on \emph{enforcement}, blocking transfers in \texttt{\_beforeTokenTransfer}
and additionally overriding the approval-based vectors (\texttt{approve},
\texttt{setApprovalForAll}) so that non-transferability holds through any
ERC-721--compliant path. The v1 contract deployed on Amoy does not expose the
ERC-5192 \texttt{locked()} view; the v2 reference contract (\cref{subsec:prototype})
adds it---returning \texttt{true} for every minted token, emitting the ERC-5192
\texttt{Locked} event at mint, and advertising interface id \texttt{0xb45a3c0e} via
\texttt{supportsInterface}---so that wallets and explorers can recognize the token
as soulbound through the standard signaling interface while our \texttt{\_beforeTokenTransfer}
hook continues to provide enforcement. We do not claim ERC-5192 is deficient---only
that, on its own, signaling without enforcement was insufficient for our goal; we
now provide both.

\subsubsection{Role-Based Access Control}

The contract defines two roles using OpenZeppelin's \texttt{AccessControl}:

\begin{itemize}
  \item \texttt{DEFAULT\_ADMIN\_ROLE}: Can grant and revoke issuer roles.
    Held by the system administrator (TOONIQ).
  \item \texttt{ISSUER\_ROLE}: Can mint new SBTs and revoke existing ones.
    Assigned to the Issuance Service's operational wallet.
\end{itemize}

This separation ensures that even if the Issuance Service's key is compromised,
the attacker cannot modify the access control structure itself.

\subsubsection{Core Functions}

The contract provides the following external functions:

\begin{itemize}
  \item \texttt{mint(address to, string uri)}: Mints a single SBT with
    the given IPFS metadata URI. Emits \texttt{SBTMinted} event.
  \item \texttt{mintBatch(address[] recipients, string[] uris)}: Batch minting
    for efficiency when issuing certificates to multiple animators
    upon project completion.
  \item \texttt{revoke(uint256 tokenId)}: Marks an SBT as invalidated
    without burning it, preserving the on-chain audit trail.
    Emits \texttt{SBTRevoked} event.
  \item \texttt{tokensOfOwner(address owner)}: Returns all token IDs
    held by a given address (view function for off-chain queries).
  \item \texttt{isRevoked(uint256 tokenId)}: Returns the revocation status.
  \item \texttt{issuedAt(uint256 tokenId)}: Returns the issuance timestamp.
\end{itemize}

% ----- 5.3 Prototype Implementation -----
\subsection{Prototype Implementation}
\label{subsec:prototype}

To demonstrate technical feasibility and on-chain correctness, we implemented a
prototype consisting of three components:
the smart contract deployed on a public testnet, an Issuance Service, and a Verification Portal.

\subsubsection{Testnet Deployment}

The \texttt{AnimatorSBT} contract was deployed on the Polygon Amoy testnet
(Chain ID: 80002) at address
\texttt{0x2cC3\allowbreak{}1B9E\allowbreak{}FBD5\allowbreak{}dDfB\allowbreak{}5456\allowbreak{}EE4c\allowbreak{}76A0\allowbreak{}fcBC\allowbreak{}A5EE\allowbreak{}E117}
(block 35{,}058{,}633).\footnote{The deployment transaction and all subsequent
interactions are publicly verifiable at
\url{https://amoy.polygonscan.com/address/0x2cC31B9EFBD5dDfB5456EE4c76A0fcBCA5EEE117}.}
A test suite of 35 unit tests was developed using Hardhat for the deployed v1
contract, covering deployment, minting, batch minting, soulbinding enforcement,
revocation, view functions, and access control; all pass. Beyond the v1 contract,
the repository adds a further 25 tests---17 for the v2 co-signing reference contract
(\cref{subsec:cosigning}), 7 for the canonical evidence-hash serialization, and a
local end-to-end issuance test---for 60 passing in total.
We note the scope of this suite plainly. The v1 and v2 contract tests exercise the
\emph{smart-contract} mechanics, which are the most standard and least error-prone
part of the system. Importantly, the serialization-determinism gap flagged in an
earlier version of this work is now closed: the \texttt{evidence\_hash} is computed
over a \emph{canonical} (recursively key-sorted) serialization, and 7 unit tests
confirm that it is independent of key insertion order, stable, and sensitive to any
value change---removing a classic source of silent hash-mismatch bugs. What the
suite still does \emph{not} cover is the live IPFS upload/pinning path and the
in-browser portal's hash-recompute logic against real pinned metadata, and---most
consequentially---the v2 co-signing contract is exercised only in the local EVM and
is \emph{not deployed on-chain}. These off-chain and on-chain-deployment gaps,
which carry the authenticity argument (\cref{subsec:verification}), remain needed
work.
An end-to-end demonstration of the Tanaka scenario
(\cref{subsec:flow}) was executed on the testnet,
successfully minting an SBT with IPFS-hosted metadata
and verifying all on-chain state (balance, token URI, revocation status).

\subsubsection{Issuance Service}

A Node.js-based Issuance Service was implemented using ethers.js~v6
and the Pinata SDK.
The service performs the complete issuance workflow:
(1)~constructing metadata JSON conforming to the schema in \cref{tab:metadata},
(2)~computing the \texttt{evidence\_hash} (Keccak-256 of the serialized attributes),
(3)~uploading the metadata to IPFS via Pinata,
and (4)~calling \texttt{AnimatorSBT.mint()} with the resulting IPFS~URI.

An end-to-end demonstration script recreates the Tanaka scenario
described in \cref{subsec:flow}:
a key animator completes 25~cuts on Episode~7, and the system
issues an SBT recording the contribution with a verifiable evidence hash.

\subsubsection{Verification Portal}

A lightweight Verification Portal was implemented as a static HTML page
using ethers.js (loaded from CDN), requiring no server-side infrastructure.
The portal accepts a wallet address, queries the contract's \texttt{tokensOfOwner()}
function, retrieves each SBT's metadata from IPFS,
and displays the contribution details including project, role, task count, and dates.
The portal also supports evidence hash verification by recomputing
the Keccak-256 hash from the IPFS metadata and comparing it
to the stored \texttt{evidence\_hash} field.

\subsubsection{Co-signing Reference Contract and Canonical Hashing}
\label{subsubsec:v2}

To make the authenticity layer of \cref{subsec:cosigning} concrete rather than
merely sketched, the repository includes a reference implementation that is
validated locally but, consistent with our scoping, is \emph{not} deployed on-chain
and does \emph{not} replace the v1 contract on Amoy:

\begin{itemize}
  \item \textbf{\texttt{AnimatorSBTV2}}: the v1 contract extended with a
    \texttt{STUDIO\_ATTESTER\_ROLE}, an idempotent multi-studio
    \texttt{coSign(uint256)} (the attester is \texttt{msg.sender}), the
    \texttt{attesters}/\texttt{attestationCount}/\texttt{hasCoSigned}/\texttt{attestationLevel}
    views, and ERC-5192 \texttt{locked()} signaling. A \texttt{coSign} costs
    \textasciitilde95{,}000 gas in the local EVM; deployment costs
    \textasciitilde2.06M gas. We report these as local-EVM figures, since the
    contract is not deployed on-chain.
  \item \textbf{Canonical serialization module}: a dependency-light, recursively
    key-sorted JSON serializer (a JCS/RFC~8785 subset) over which
    \texttt{evidence\_hash} is computed, so that two parties building the same
    attributes in different key order obtain the same hash. This closes the
    hash-determinism gap previously flagged as untested.
  \item \textbf{Issuance Service v2}: the v1 issuance flow extended with the
    canonical hash and an optional co-signing step using a separate attester wallet,
    plus a swappable wallet-provisioning seam (a non-custodial embedded-wallet
    interface) that is currently an unconfigured skeleton.
\end{itemize}

We emphasize what this does and does not establish: it demonstrates that the
co-signing mechanism, canonical hashing, mint, and soulbinding \emph{compose}
correctly off-chain and in the local EVM. It does not establish on-chain behavior,
independent-studio operation, or end-to-end issuance from real application data---all
of which remain future work (\cref{subsec:eval_limitations}).

% ----- 5.4 Integration with Production Management Client -----
\subsection{Integration with Production Management Client}
\label{subsec:integration}

AnimatorSBT is designed for integration with
\textit{Pocket Seishin},\footnote{Available
at \url{https://pocket-seishin.vercel.app}.}
a Progressive Web Application developed by the authors
for freelance animators to manage cuts and finances.
The application is publicly deployed, and cut-level work logs are stored locally
on the animator's device, preserving privacy by default.
We state the integration status plainly: the SBT issuance pipeline described below
is \emph{not yet integrated} into Pocket Seishin, and \emph{no SBTs have been
minted from real user data}. The end-to-end demonstration of \cref{subsec:prototype}
used a scripted work log, not live application data.
SBT issuance would occur only with the animator's explicit consent.
The remainder of this subsection therefore describes a \emph{planned} integration.

The planned integration follows the issuance flow
described in \cref{subsec:flow}.
The key integration points are:

\begin{enumerate}
  \item \textbf{Wallet provisioning:}
    When a new animator registers on Pocket Seishin,
    an embedded wallet will be created using account abstraction.
    The wallet address will be stored in the user profile
    and used as the \texttt{to} parameter for SBT minting.
    The animator will not be required to interact with the wallet directly.
  \item \textbf{Work log aggregation:}
    Pocket Seishin already records cut-level task data
    (assignment, status transitions, completion timestamps)
    as part of its core functionality.
    Upon user consent, this locally stored data will be used
    to construct the SBT metadata.
  \item \textbf{Evidence hash computation:}
    The Issuance Service will compute a Keccak-256 hash of the serialized work log
    entries for the certification period.
    This hash will be included in the SBT metadata (\texttt{evidence\_hash} field)
    and can later be verified against the user's local data.
  \item \textbf{Certificate display:}
    Pocket Seishin's profile page will include an ``SBT Certificates'' section
    that renders the animator's issued tokens with project title,
    role, task count, and a link to the Verification Portal.
\end{enumerate}

From the animator's perspective, the entire SBT workflow will be transparent:
they will continue using the PMC as before, and contribution certificates
will appear automatically upon project milestones.
No blockchain knowledge, wallet management, or additional data entry will be required.
